# Merging Creature Extractions

## Overview

The `extract` WeiDU component (`extract/extract.tp2`) writes every `.cre` in `override/` directly to `extract/csv/source.csv`, semicolon-delimited. The **first line of `source.csv` is its own header** — the script reads the column names from that line rather than hard-coding them, so adding or removing columns in `extract.tp2` needs no change here. The current layout is:

```
file;general;race;class;anim;deathvar;dialog;level;gender;sex;allegiance;overrideScript;classScript;raceScript;generalScript;defaultScript;helmet;shield;lring;rring;amulet;weapon1;weapon2;weapon3;weapon4;xpv;name
```

`file` (the resref) is always first and `name` (the display name) is always last — `name` is unquoted, so it can safely contain any character, including a literal `;` or `"`. The component truncates `source.csv` and rewrites it from scratch on every run, so running it after each mod install produces a full, clean snapshot of the current override folder — not just that mod's additions, with no manual copy/paste step and no interleaved WeiDU log noise to filter. `BUT_ONLY` means it never actually writes back any `.cre` file (nothing is patched, only read), so installing and uninstalling this component is a no-op on the game itself.

`scripts/extract-creatures.js` then compares a snapshot of `source.csv` against the accumulating master list (`extract/csv/creatures.csv`, which is the same columns with an added `origin` column just before `name`) so you know which mod introduced each creature. The mod name is passed explicitly as `--origin` rather than derived from a filename. **The `origin` column is immutable**: it is set once, to the mod that first introduces a creature, and is never reassigned — a later mod that modifies the creature does not take origin over. **Every column except `file`, `name`, and `origin` is a tracked field**: when a mod changes an existing creature's `general`/`race`/`class`/`anim`/`deathvar`/`dialog`, its scripts, its equipped items, `level`, `xpv`, allegiance, etc., the script applies the new values to `creatures.csv` (last mod processed wins on field *values*, but `origin` stays put) and logs the old-vs-new diff for visibility — it does NOT ask you to reconcile by hand. A `name`-only difference is never flagged or applied — display-name changes don't affect gameplay. A `name` field of exactly `<Invalid Strref -1>` (a `.cre` whose display-name strref doesn't resolve) is normalized to an empty string as it's read.

This keeps `creatures.csv` always reflecting your current install, and means later mods' logs report only what THEY changed, not a growing backlog of everything every prior mod already changed.

**Per-install history.** Any run that adds or modifies a creature — or migrates the column layout — copies the extraction verbatim to `extract/csv/history/<NNN>_<origin>.csv`, where `<NNN>` is a zero-padded global counter (`001`, `002`, …) — the next number after the highest already in the folder. A clean re-run that changes nothing writes no snapshot and consumes no number: its extraction would be byte-identical to the one already saved, and the summary line says `no changes — no history snapshot`. Whenever that run added or modified any creature, a companion `extract/csv/history/<NNN>_<origin>_changes.log` records the install's footprint: a `<origin>: N new, M changed` count line, then a `NEW` section and a `CHANGED` section (each omitted when empty). Every creature line is `<resref>  <display name>` (resref alone when unnamed); modified creatures are followed by their indented field-level old -> new diffs. The bootstrap run (`--origin base`/`bg1` into an empty `creatures.csv`) gets no log — its `001` snapshot already *is* the full initial roster. These files are immutable: never overwritten or deleted, so a mod installed in several passes (`--origin stratagems` more than once) leaves one numbered pair per pass, each log showing only that pass's incremental footprint. Use them to look up what any creature looked like at an earlier point, or which pass of which mod last touched it.

**Input cleanup.** When the script reads its default `source.csv` (no `--source` given) and finishes with no warnings, it deletes that `source.csv` — the raw extraction has no further use once merged, and removing it stops a later stray run from silently reading stale data. An explicitly passed `--source <path>` is the caller's file and is always left in place, as is a `source.csv` from a run that emitted warnings (inspect it, fix the snapshot). The documented procedure below passes `--source …source.csv.snapshot`, so the script never auto-deletes there and step 5 still removes the snapshot by hand.

**Column migration.** If `creatures.csv` predates a column you later add to `extract.tp2`, the next run realigns it to the current column set, backfilling the new column for existing creatures from the current extraction (or an empty string if that creature isn't in it). This realignment is silent — it is not reported as a per-creature change.

Because installing `extract` is otherwise pointless clutter in `WeiDU.log`, the full procedure installs it, snapshots `source.csv` somewhere the component doesn't manage, then immediately uninstalls it again — leaving no trace except the updated `creatures.csv`, `history/`, and log. The merge script runs against that snapshot rather than `source.csv` directly (via `--source`), which decouples it from the install/uninstall cycle: once uninstall returns you can start installing the next mod right away, without waiting for the merge script to finish. Order still matters within the cycle itself: uninstalling deletes `source.csv` along with everything else the component created, so the snapshot copy must happen before uninstall, not after.

## Procedure

1. Install the `extract` component: `weidu.exe extract/extract.tp2 --yes --force-install 0` (run from the game root, where `weidu.exe` lives). This (re)writes `extract/csv/source.csv` from scratch to reflect the current `override/` folder.
2. Copy the snapshot before it can be deleted: `cp extract/csv/source.csv extract/csv/source.csv.snapshot`. WeiDU's uninstall only reverses files *it* wrote, so a differently-named copy survives step 3 untouched.
3. Wait a second for the filesystem to settle, then uninstall: `sleep 1 && weidu.exe extract/extract.tp2 --uninstall` (the global `--uninstall` flag, not `--force-uninstall` — the latter was found unreliable and can silently reinstall instead). This removes `source.csv`, the `extract/backup` folder, and the `WeiDU.log` entry. The delay is a stability margin after the copy/install churn, not a proven requirement — drop it if it turns out not to matter. Once this returns, it's safe to start the next mod's install — you don't need to wait for step 4.
4. Run: `node <plugin-path>/skills/extract-creatures/scripts/extract-creatures.js --origin cdtweaks --destination extract/csv/creatures.csv --source extract/csv/source.csv.snapshot`
   (`--destination` defaults to `extract/csv/creatures.csv` relative to the current directory if omitted; `--source` overrides the default input path of `source.csv` next to the destination — required here since that file no longer exists after step 3; `--history` overrides the default history directory of `history/` next to the destination). Any warnings here indicate a genuine problem in the snapshot, not routine WeiDU noise — the component's output is already clean.
5. Delete the snapshot: `rm extract/csv/source.csv.snapshot`.
6. Read the summary line from step 4:
   - New creatures are already appended to `creatures.csv` with `origin=cdtweaks`.
   - Any existing creature whose tracked fields changed is updated in `creatures.csv` with the new field values; its `origin` is left unchanged — it keeps the mod that first introduced it.
   - `extract/csv/history/<NNN>_cdtweaks_changes.log` lists this install's footprint — the count line, the added resrefs, and each modified creature's field diff — for visibility; nothing to reconcile by hand.
   - `extract/csv/history/<NNN>_cdtweaks.csv` is the full extraction as it stood right after this install. If the install changed nothing, no snapshot (and no log) is written and the summary says so.
7. To bootstrap `creatures.csv` from scratch, run this same procedure against a vanilla/base install with `--origin base` against an empty (or nonexistent) destination — every row is "new" and gets `origin=base`, and `history/001_base.csv` captures the vanilla extraction. The destination's parent directory (e.g., `extract/csv/`) must already exist; only the destination file itself may be missing.

## Common Mistakes

- Uninstalling (step 3) before copying the snapshot (step 2) — this deletes `source.csv` before it's been read, losing the extraction.
- Using `--force-uninstall` instead of `--uninstall` for step 3 — in testing, `--force-uninstall N` silently reinstalled the component instead of removing it; the global `--uninstall` flag is the one that actually works.
- Forgetting `--source` on step 4 — the script falls back to `source.csv` next to the destination, which no longer exists after step 3, so it fails fast with `input file not found` rather than silently reading stale data.
- Reusing the same `--origin` name across two *different* mods — the origin label and the history filenames both come from that argument, so each mod needs its own distinct name. Reusing it deliberately for a *second pass of the same mod* is fine and expected: it just adds another numbered history pair.
- Assuming a `_changes.log` means action is needed — it's an applied-change record, not a pending decision. Only check it if a creature looks wrong and you want to know which mod pass last touched it.
